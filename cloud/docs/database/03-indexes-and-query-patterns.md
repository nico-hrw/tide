# Database Indexing Strategy & Query Execution Patterns

This document defines the indexing architecture, query optimization patterns, and performance considerations for the SQLite data layer implemented in `cloud/internal/store/`.

---

## 1. Indexing Philosophy

The storage engine uses SQLite in **Write-Ahead Logging (WAL)** mode. SQLite indexes are implemented as B-trees that store index keys and pointers to the rowid (or clustered primary key).

### 1.1 Read vs. Write Trade-offs
- **Sub-millisecond Point Lookups & Range Scans**: Read queries on hot paths (file trees, auth verification, Yjs log replays) must execute in `< 1ms` by hitting B-tree indexes directly (`SEARCH TABLE ... USING INDEX`).
- **Mitigating Write Amplification**: Every secondary index requires an additional B-tree write on `INSERT`, `UPDATE` (if indexed columns change), and `DELETE`. In high-throughput append scenarios (e.g., collaborative Yjs updates and WAL flushes), unneeded secondary indexes degrade disk I/O and increase WAL checkpoint latency.
- **Left-to-Right Prefix Rule**: Multi-column composite indexes are carefully ordered by selectivity: `(equality_column, equality_column, range_or_sort_column)`.
- **Zero-Knowledge Blind Indexing**: Due to end-to-end encryption (E2EE), personal identifiable identifiers (PII) like email addresses and usernames are never stored in plaintext. They are indexed via deterministic blind indexes (HMAC-SHA256 keyed hashes) enabling exact-match equality lookups without exposing user credentials.

## 2. Complete Index Catalog

### 2.1 `users` Table
Stores user accounts and tenant credentials.

| Index Name / Type | Columns | Purpose | Index Type |
|---|---|---|---|
| `sqlite_autoindex_users_1` | `id` | Primary key lookup | Clustered B-tree (Unique) |
| `idx_users_email_blind` | `email_blind_index` | Exact-match user lookup during login / password reset | Secondary B-tree (Unique) |
| `idx_users_username_blind`| `username_blind_index` | Uniqueness validation and user handle resolution | Secondary B-tree (Unique) |

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email_blind ON users(email_blind_index);
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_username_blind ON users(username_blind_index);
```

### 2.2 `files` Table
Stores documents, folders, metadata, and virtual drive trees.

| Index Name | Columns | Purpose | Index Type |
|---|---|---|---|
| `sqlite_autoindex_files_1` | `id` | Primary key lookup | Clustered B-tree (Unique) |
| `idx_files_user_id` | `user_id` | Tenant isolation; fetch all files belonging to a user | Secondary B-tree |
| `idx_files_parent_id` | `parent_id` | Child listing for directory views; recursive folder CTEs | Secondary B-tree |
| `idx_files_status_trashed_at`| `status, trashed_at` | Trashed item management, soft-delete filtering, and purge sweeps | Composite Secondary B-tree |

```sql
CREATE INDEX IF NOT EXISTS idx_files_user_id ON files(user_id);
CREATE INDEX IF NOT EXISTS idx_files_parent_id ON files(parent_id);
CREATE INDEX IF NOT EXISTS idx_files_status_trashed_at ON files(status, trashed_at);
```

### 2.3 `file_shares` Table
Manages permission grants and access control lists (ACLs) between users.

| Index Name | Columns | Purpose | Index Type |
|---|---|---|---|
| `idx_file_shares_unique` | `user_id, file_id` | Prevents duplicate share records; instant permission checks | Composite Unique B-tree |
| `idx_file_shares_user_id` | `user_id` | "Shared with Me" queries listing accessible files for a user | Secondary B-tree |
| `idx_file_shares_file_id` | `file_id` | Collaborator discovery for a given file | Secondary B-tree |

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_file_shares_user_file ON file_shares(user_id, file_id);
CREATE INDEX IF NOT EXISTS idx_file_shares_user_id ON file_shares(user_id);
CREATE INDEX IF NOT EXISTS idx_file_shares_file_id ON file_shares(file_id);
```

### 2.4 `yjs_wal` (Collaborative Document WAL)
Stores append-only binary updates generated by Yjs collaborative editing sessions.

| Index Name | Columns | Purpose | Index Type |
|---|---|---|---|
| `PRIMARY KEY` | `file_id, seq_id` | Composite primary key. Replaces rowid. Sequential log scan starting from a client vector clock | Clustered Composite B-tree |

```sql
CREATE TABLE IF NOT EXISTS yjs_wal (
    file_id TEXT NOT NULL,
    seq_id INTEGER NOT NULL,
    update_data BLOB NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (file_id, seq_id)
) WITHOUT ROWID;
```
*Note: Using `WITHOUT ROWID` or a composite clustered primary key ensures that range scans `WHERE file_id = ? AND seq_id > ? ORDER BY seq_id ASC` directly traverse contiguous leaf pages without secondary index pointer lookups.*

## 3. Critical Query Patterns & Execution Plans

### 3.1 Recursive Folder Hierarchy Traversal (Common Table Expressions - CTE)
To build a file tree, compute aggregate folder sizes, or traverse down a sub-tree for recursive operations (e.g., bulk moves, permissions inheritance, or cascading deletes):

```sql
WITH RECURSIVE folder_tree(id, parent_id, name, path, depth) AS (
    -- Anchor: root folder or selected directory
    SELECT id, parent_id, name, name AS path, 0 AS depth
    FROM files
    WHERE id = ? AND user_id = ? AND status != 'trashed'

    UNION ALL

    -- Recursive member: child nodes
    SELECT f.id, f.parent_id, f.name, (ft.path || '/' || f.name), ft.depth + 1
    FROM files f
    JOIN folder_tree ft ON f.parent_id = ft.id
    WHERE f.status != 'trashed'
)
SELECT * FROM folder_tree ORDER BY depth ASC, name ASC;
```

#### Execution Plan (`EXPLAIN QUERY PLAN`):
```text
QUERY PLAN
|--CO-ROUTINE folder_tree
|  |--SETUP
|  |  `--SEARCH files USING INDEX sqlite_autoindex_files_1 (id=?)
|  `--RECURSIVE STEP
|     |--SCAN ft
|     `--SEARCH f USING INDEX idx_files_parent_id (parent_id=?)
|--SCAN folder_tree
`--USE TEMP B-TREE FOR ORDER BY
```
- **Optimization Benefit**: The recursive step evaluates `SEARCH f USING INDEX idx_files_parent_id (parent_id=?)` for each depth level. This eliminates a full table scan across the entire file storage on every directory step, keeping folder tree resolution $O(K \log N)$ where $K$ is the number of descendants.

### 3.2 Date-Filtered Todos and Task Management Queries
Dashboards display unfinished tasks filtered by upcoming due dates or overdue status:

```sql
SELECT id, title, due_date, priority, parent_id
FROM todos
WHERE user_id = ?
  AND status = 'pending'
  AND due_date BETWEEN ? AND ?
ORDER BY due_date ASC;
```

#### Execution Plan:
```text
QUERY PLAN
`--SEARCH todos USING INDEX idx_todos_user_status_due (user_id=? AND status=? AND due_date>? AND due_date<?)
```
- **Composite Index Alignment**:
  - `user_id`: Exact match (equality prefix)
  - `status`: Exact match (equality prefix)
  - `due_date`: Range scan (`BETWEEN ? AND ?`)
  - Because `due_date` is the terminal column in the composite index, SQLite retrieves rows in index order without invoking an extra temporary B-tree sort (`USE TEMP B-TREE FOR ORDER BY`).

---

### 3.3 Trashed File Retention Purge
A background retention worker periodically permanently purges items soft-deleted more than 30 days ago:

```sql
DELETE FROM files
WHERE status = 'trashed'
  AND trashed_at < datetime('now', '-30 days');
```

#### Execution Plan:
```text
QUERY PLAN
`--SEARCH files USING INDEX idx_files_status_trashed_at (status=? AND trashed_at<?)
```
- **Index Efficiency**: Rather than scanning millions of active documents, the query narrows directly to the `status = 'trashed'` partition of the B-tree and performs a bounded range scan on `trashed_at`.

---

### 3.4 Yjs Delta Replay & Vector Clock Sync
When a collaborative editor reconnects, it supplies the highest sequence ID it currently holds:

```sql
SELECT seq_id, update_data
FROM yjs_wal
WHERE file_id = ?
  AND seq_id > ?
ORDER BY seq_id ASC;
```

#### Execution Plan:
```text
QUERY PLAN
`--SEARCH yjs_wal USING PRIMARY KEY (file_id=? AND seq_id>?)
```
- **Sequential Streaming**: The composite primary key `(file_id, seq_id)` guarantees sequential disk locality. SQLite performs a binary search to find `(file_id, client_seq + 1)` and then scans forward linearly through consecutive B-tree leaf nodes.

## 4. SQLite Query Optimization Guidelines

### 4.1 Avoiding Full Table Scans (`SCAN TABLE`)
In production logs and diagnostics, any query showing `SCAN TABLE` on core data tables (`files`, `users`, `todos`, `yjs_wal`) indicates a missing index or un-indexed predicate. Always verify query structure against available indexes.

### 4.2 Interpreting `EXPLAIN QUERY PLAN`
Run `EXPLAIN QUERY PLAN <sql>` during development or review:
- `SEARCH TABLE ... USING INDEX ... (col=?)`: Ideal point or bounded range lookup using B-tree.
- `SCAN TABLE ...`: Full table traversal. Unacceptable for tables growing unbounded.
- `USE TEMP B-TREE FOR ORDER BY`: SQLite must materialize and sort result rows in memory/temp storage because the index order does not match the `ORDER BY` clause. Add sort columns to the index tail if this occurs on hot paths.
- `USE TEMP B-TREE FOR DISTINCT`: Occurs when deduplicating results without an index.

### 4.3 Composite Index Ordering Rules
Always structure composite indexes with:
1. **Equality columns first**: `WHERE colA = ? AND colB = ?`
2. **Range / Sort columns last**: `WHERE colC > ? ORDER BY colC`
*(Any column placed after a range condition cannot be used for binary index searching).*

### 4.4 SQLite Optimizer Statistics & `ANALYZE`
SQLite makes decisions based on estimated cost. If a table has skewed data distribution, periodic execution of:
```sql
PRAGMA optimize;
```
prior to closing the database connection updates `sqlite_stat1`, allowing the query planner to choose between competing indexes effectively.

### 4.5 Write Amplification & WAL Checkpointing
To keep commit times under 2ms:
1. Limit indexes per table to $\le 4$ unless justified by critical query latency requirements.
2. Enable WAL autocheckpoint (`PRAGMA wal_autocheckpoint = 1000;`).
3. Set `PRAGMA synchronous = NORMAL;` to maintain ACID guarantees with minimal sync barrier overhead in WAL mode.
